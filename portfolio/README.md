# 项目组合分析系统

把人员技能、项目依赖、预算与收益假设放在一起做组合级排程与评估。**每个项目单独最优的排期拼不出可执行组合**——共享人员会在项目间互相挤占，本系统把这种资源竞争显式建模并算进结果。

纯 Python 标准库（`http.server` + `sqlite3`）+ 原生前端，无任何第三方依赖。

## 运行

```bash
cd portfolio
python3 server.py          # 默认 8000 端口
# 打开 http://localhost:8000
```

测试：`python3 tests.py`（19 个用例：调度不变量、资源竞争有效性、版本冲突、冻结校验、API 冒烟）。

## 核心模型

- **时间轴**：周（float）。`now=6`，之前已发生不可改，之后才可调度。
- **人员**：技能等级（如 后端:3）、周成本、产能。同一时刻只能做一个任务。
- **阶段**：工作量（人周）、所需技能与最低等级、依赖（项目内写阶段 id，跨项目写 `项目/阶段`）。
- **切换成本**：人员跨项目切换损失 0.5 周（可调），占用该人员但不产出进度。
- **收益**：每个项目一组 `{概率, 年化收益}` 情景；项目完成才开始产生收益，horizon 内实现收益 = 期望年化 × 剩余周数/52。
- **冻结**：已开始/已完成的阶段（执行记录）位置与执行人固定，任何新方案不得移动。

## 两种排程策略（同一套资源约束）

| 策略 | 排序规则 | 倾向 |
|---|---|---|
| 关键路径优先 | 目标完成周 − 关键链长度，余量小者优先 | 保工期、少超期 |
| 预期收益优先 | （本项目 + 被卡住的下游项目）期望年化收益 ÷ 关键链 | 保组合期望价值 |

基线数据下两者结果明显不同：收益优先净期望更高，但推荐系统会超期 4 周——取舍由计划员判断，系统只把账算清楚。

## 事前评估，不搞事后诸葛亮

- 所有指标（期望净收益、P10/P50/P90、亏损概率）只由**假设中的概率分布**推出（蒙特卡洛 2000 次，固定种子可复现）。
- 已确认方案保留**确认时点的快照**；之后执行记录变化不会回写改数——评价一个决策只能用它当时能知道的信息。
- 执行页可以录入"实际开始"，但它影响的是**未来草案**的约束，不用来给旧方案打分。

## 多计划员并发

- 每个方案带 `version`；保存/确认必须带上自己看到的版本号，不一致返回 **409**，后提交者刷新重来，不会悄悄覆盖别人的修改。
- **确认**时重新校验：已开始/已完成阶段的工期、技能要求、执行人若被方案修改，返回 **422** 并列出全部冻结冲突。

## 页面

1. **假设与方案**：编辑策略/horizon/切换成本/人员技能/项目收益情景/阶段依赖，保存即重算；可确认、可恢复为草案。
2. **甘特图**：按人员（资源视角）或按项目（阶段视角）；点击任意色块追踪"谁在占用、为什么此时开始"（含等待原因与切换成本）。
3. **冲突与瓶颈**：资源等待列表（谁被谁卡住、卡几周）、技能等级带负荷（瓶颈只在最高等级带暴露，如 数据≥3 只有赵敏）、人员利用率。
4. **方案比较**：2–4 个方案的事前指标并排、各项目完成周对比、最优项高亮；可一键把某方案恢复为新草案再算。
5. **执行与确认**：执行记录（冻结事实）、标记阶段开始（演示冻结校验）。

## 代码结构

```
scheduler.py   调度引擎：串行 SGS + 最早空档放置 + 切换成本 + 冻结钉死 + 事前指标
seed.py        虚构数据：8 人 / 7 项目 / 30 阶段，瓶颈与跨项目依赖经过设计
store.py       SQLite 持久化 + 乐观版本锁 + 确认/恢复
server.py      REST API + 静态页面（仅标准库）
static/        原生 JS 单页应用
tests.py       19 个测试
```

## 设计取舍（规模可控）

- 一个阶段一个负责人（不拆分），切换成本按项目对计算；
- 蒙特卡洛只抽收益情景，不抽工期不确定性；
- 执行记录全局唯一（现实只有一份），方案各自持有假设。
